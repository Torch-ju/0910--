# 决策记录

记录决定及其来源，不记录动态进度。状态使用“有效”“被替代”“待决定”；决定类型区分“用户确认”与“工程选择”。用户确认源于本项目当前对话，不伪造更早时间或消息 ID。新信息改变决定时保留旧理由并指向后继 ID。

## D-010 | 最终实施基线

类型：用户明确确认并授权实施。状态：有效。

决定：双场景为西方魔幻与东方武侠，场景只提供世界引导；NPC 动态提取和生成，未提人物时主动建议；初始时间线限世界历史与开局；故事框架 Agent 先于 NPC Agent。真实兼容模型接入提前，首次联调最多 10 次，含失败及修复。此决定替代 D-006 中先完成纯演示再接模型的执行顺序，D-002 的首期范围相应明确纳入初始时间线。

## D-001 | 共创是产品核心

类型：用户确认。状态：有效。来源：用户明确提出“我们的核心是AI和用户一起完成故事”，并认可共创流程。

决定：用户始终掌握方向、修改与最终确认；AI 理解、追问、建议、整理并维护一致性。功能定义见 SPEC-L1 一至三。

理由：后续实现需要保留讨论与选择过程，不能将用户降为一次性生成后的审核者。

## D-002 | 先完成第一层

类型：用户确认。状态：有效。来源：用户反复指定“前端交互、自然语言输入、识别、角色画像.json、故事世界.json，第一层（初步）”。

决定：以共同形成并保存基础设定作为第一层终点。连续剧情、章节、压缩、长期记忆、账号、云同步和 DOCX/PDF 导出属于后续范围，详见 SPEC-L1 二。

理由：先交付可继续扩展的共创基础，不以未来架构替代首期实现。

## D-003 | 简约美学工作台

类型：用户确认（简约美学与共创交互）；工程选择（具体纸张色、墨色与强调色）。状态：有效。

决定：采用文学编辑台的阅读气质，桌面对话与结构化状态并列，移动端顺序组织；来源标签和编辑确认清晰可见。具体色值是可逆设计选择，不是用户冻结的品牌资产。详见 SPEC-L1 五、六。

## D-004 | 识别的首期含义

类型：用户认可的需求整理。状态：有效。

决定：自然语言理解、意图/实体/关系/约束提取和歧义冲突识别。首期不包含 OCR、图片或人脸识别；用户输入不够完整时允许必要澄清及明确标记的建议。详见 SPEC-L1 七。

## D-005 | 正式 JSON Schema 契约

类型：用户确认（JSON Schema 与详细描述）；工程选择（Draft 2020-12 与文件组织）。状态：有效。

来源：用户明确要求“json 应该是 json schema 的，要做好描述”。

决定：共享、故事世界和角色画像分别有正式 Schema，实例须通过校验；类型、Schema、示例各有职责。字段说明、来源、状态、锁定、版本及引用完整性必须落到实现，详见 SPEC-L1 八、九。

未决范围：校验库和具体类型生成工具在工程初始化时依据实际依赖确认；当前选择 Schema 方言不等于安装了依赖。

## D-006 | 演示与真实模型分开验收

类型：工程选择，来自已获用户认可的首期方案。状态：有效。

决定：Next.js App Router、React、TypeScript strict 为待落地默认技术方向；已有真实工程和手册优先核对。允许显式演示 Provider 先完成交互，但真实语义理解能力须有模型联调证据。接口和密钥在服务端边界管理。

模型供应商、具体模型、预算、生产部署均待决定。不得因文档写了默认方案就标记实现或付费调用已获授权。

## D-007 | 唯一项目记忆库

类型：用户确认。状态：有效。来源：本轮用户要求把提示词整理为开发文档，并维护唯一 agent/readme/memory，避免本意和进度丢失。

决定：项目使用一个根目录 AGENTS.md、一个 README.md、一个功能规格以及 memory 下的索引、CURRENT、DECISIONS、HISTORY。CURRENT 是唯一进度源。

理由：规则、需求、决定、现状与历史分工明确；不重复维护多个提示词和 handoff。无需为此创建新对话。旧提示词路径只导向功能规格。

## D-008 | 数据契约的冲突统一

类型：工程选择，对已有详细要求作一致化整理。状态：有效。

决定：关系实体只放角色文档顶层，角色内使用 relationship_ids；source/status/locked 分开；成长方向的确认派生自事实状态；空 JSON 示例明确为结构占位，正式实例须补齐。详情只见 SPEC-L1 九。

理由：旧提示词中同时存在角色内嵌关系与顶层关系两种描述，直接照搬会形成两份权威数据。此决定保留原功能意图并统一存放规则。

## D-009 | 幂等与证据接续

类型：用户要求（必要幂等与索引）；工程选择（稳定 ID 和串行维护）。状态：有效。

决定：文档维护使用稳定 operation_id，重试更新同一事件；产品未来更新使用操作 ID 与基础版本保护重复提交和旧响应。当前文档机制见 AGENTS，产品实现要求见 SPEC-L1 十二。

理由：恢复时能区分已做、未做和失败部分，减少重复生成、丢失新修改或重复计入进度。文档约定不等于已实现运行时幂等。


## D011：公共完整 Schema 与模型内部精简投影分开

公共三份 Draft 2020-12 Schema 继续作为导出、类型和应用校验的权威。模型内部协议由其投影得到，不另手工维护一套公开数据结构。模型 Fact 只填写 value、source、evidence；状态、锁定、时间戳、修订和系统 ID 头由应用恢复并校验，避免输出冗长和模型越权。人物数量、时间线内容、丰富画像字段不因精简传输而裁剪。精简不放宽正式 Schema，也不以删除不合格实体进行修复。

## D012：文本模型、真实预算与证据分级

用户最终明确选择 doubao-seed-2-0-pro-260215，兼容服务为 https://api.openai-next.com。不使用 Seedream 图像模型替代文字理解。密钥仅本地配置；最多 10 次联调由持久账本约束，所有实际尝试和一次结构修复计数。

连通性探针成功、合成接口测试通过、真实业务链路成功是三种不同证据。不得用任何前两者代替第三者。最新实际数值仅维护在 CURRENT 和运行账本，不在决策文档另设可漂移的计数。

## D013：本地预览和单一文档权威

第一层只提供单机开发/生产预览。浏览器存储创作快照，服务端保存模型操作结果和累计额度；不引入账号、云同步或外部发布。README 维护运行入口，AGENTS 维护唯一项目行为规则，PRODUCT_SPEC 维护功能边界，memory/CURRENT 维护唯一进度。Next 自动追加 Agent 规则关闭；项目运行包装器只在子进程禁用遥测，避免修改用户全局配置。

## D014：字段级共创与候选三方合并（继承 D011/D012）

用户明确要求每个创作字段都有 AI 建议，而非仅显示“AI 建议”来源标签。沿用一个文字模型，以公共 Schema 派生字段输出约束，结合字段专属任务提示；输入分离共同 story_idea、历史用户补充与本次 instruction。公开两份数据实例和三份 Schema 的权威不变。

采用候选不再把“版本不同”直接等同于“冲突”。保留生成基线并按稳定 ID 三方合并，真正同字段冲突、锁定与故事方向变化仍阻止采用。过期且缺少基线的旧候选不能绕过保护。

采用世界后默认自动生成 NPC 候选，仍保留用户确认边界和关闭开关。模型额度是全链路共享的原 10 次总上限，不随字段数增加或服务重启而扩大。


## D015：应用层不设置请求次数上限

用户明确要求取消本地请求次数限制。运行账本继续记录每次请求及重放信息，用于审计和状态展示，但不再以累计次数阻止新的模型调用；实际可用额度、速率限制和计费边界由模型服务商及密钥配额决定。



## D016：完整 PRD 与确定性主 Agent 编排

来源：2026-09-12 用户明确要求整合全部文档和 Agent，生成完整 PRD、调用规则并实现主 Agent。该授权扩展此前仅第一层的范围，不扩展为公开发布或商业系统。

完整产品需求与调用契约按用户要求置于当前工作区根目录 ../PRD.md 和 ../MAIN_AGENT_RULES.md；第一层 PRODUCT_SPEC 保留细节，新增范围以 PRD FR/AC 为依据。这是 D013 文档职责的扩展，不建立第二份开发进度库。

主 Agent 使用确定性状态机，设定操作复用已有四个 Agent；写作依次执行角色、旁白、转写、记忆、摘要与章节。章节归档是确定性工具。新增角色/旁白/摘要模型适配，修正转写对象契约。子 Agent 不能自行写权威故事。

本地写作会话采用单故事文件、校验和、目录锁、逐步检查点和原子提交；与第一层浏览器草稿分开。动态记忆重放已验证抽取日志，复用独立模块的核心逻辑，以确定性 ID 和时间戳保持可恢复；不在本轮引入分布式数据库事务。该决定扩展 D013 的本地存储边界，不覆盖既有初始设定。

为复用 memory-agent 的 NodeNext 源码，Next.js 使用 webpack extensionAlias，并将 dev/build 显式固定为 webpack。已有锁定的 Zod 4.6.2 提升为根应用直接运行依赖，无版本升级。

限制：同步 API、本地单用户、无正式写作 UI、无真实模型全链路验收、无自动放弃未完成轮次、无写作中初始设定同步。模型费用上限继续遵循 D015；本轮只用合成数据检查，未调用真实模型。


## D017 — 本地写作产品与可复现交付

- 用户授权扩展为完整本地待办及真实模型验收，公网发布不作为本地完成前提。
- 连续写作使用持久任务标识与响应后执行；不自动重发进程重启后的未知付费步骤。取消等待、取消后续步骤与放弃轮次分开。
- 作品管理和人工记忆修正通过同一故事锁、叙事版本及审计回执提交；备份不覆盖同 ID 文件，派生缓存重建。
- PRD 和调用规则以仓库内文件为权威，上级工作区保留同步副本，替代 D016 的“仅外层根目录交付”安排。
- 真实错误证明 NPC 提示只附 $defs 会遗漏外层对象结构；补完整根 Schema 与定位明确的修复提示，不放宽返回校验。

## D018：设定候选自动接续（OP-20260912-011）

用户要求根据输入自动识别并生成画像和世界时间线，替代D017及OP010中先采用世界、回答关键问题再生成NPC的流程。世界候选有效即可接续NPC；缺失细节标为建议，不冒充确认。全部结果仍经候选采用，叙事初始化仍校验确认和矛盾。失败保留已完成阶段并显式续试。

## D019：直接开篇与自主续写（OP-20260912-012）

用户明确取消写作前置确认，覆盖原叙事启动需所有非空字段确认、关键问题解决的要求。有效结构和现有输入即可开始，模型补全故事不更改原静态事实权限。开始自动开篇，留空可续写，正文无固定字数校验。指定skill用于创作方法，不作真人身份声明；未来计划与既成事实分开。

## D020：用户授权的API自动恢复（OP-20260912-013）

替代先前每次失败恢复都需明确确认的产品交互。保存的设定请求自动恢复原输入；成功与可重新校验的旧结果先复用，网络失败最多两次自动补试，保留账本。持续失败停止自动循环，允许用户继续按钮无确认重试。适用本地单进程，不声称跨部署恰好一次。


## D021：确定性修复、合并规划和正文预览（OP-20260912-014）

用户采纳提速方案。以本地计算替代关系索引的模型修复，保留遗漏的既有人物；人物与故事线合并规划，使正常每轮4次模型调用。原skill全文仍归档，运行时只提供精简方法及必要设定信息，不压缩正文目标。

正文预览与正式提交明确分开：可提前阅读，不能用于记忆/摘要/导出，整轮成功后再正式提交。真实供应商时间不由离线调用数量推算。此决定替代D016的角色、旁白各自付费执行安排，保留步骤依赖和恢复规则。并发保护限单进程本地部署，不宣称分布式幂等。

## D022：叙事软预算与场景推进（OP015）

真实开篇被 operations 请求指纹计入上下文导致预算拦截，随后正文从开场推进到黄昏山洞又被逐字场景一致性拒绝。用户要求依据已有条件直接生成完整故事，因此上下文排除运行元数据，软预算仅控制附加历史；核心事实仍传入。正文结束场景可以与规划开场不同，保留双方结果供追溯，事实证据仍校验。失败步骤有成功模型回执时复用已有结果再校验，不默认重新付费。此决定替代旧契约中的逐字场景相等与核心设定软预算门禁。


## D022：直接创作优先（OP-20260912-016）

用户要求继续缩短生成等待，采用一次调用合并人物、故事线和正文，新轮次不再付费预先规划。原D021的四调用流程仅保留用于旧轮次恢复，新轮次三调用。后台记忆/摘要不阻塞阅读，但仍需完成后才能推进下一轮；避免以并发破坏记忆依赖。短场景真实测速用于验证当前API流式能力，不按短文本数据承诺长文完成时间。


## D023：用户掌握主角对话决定（OP-20260913-018）

用户明确要求NPC对话与主角参与。新互动轮次覆盖D019/OP012中可自主代主角作答与关键决定的部分；模型只推进背景与NPC，遇到需要主角回应的对话停笔。结构化dialogue来自同一次正文生成，不用引号正则代替对话理解，不增加分类模型调用。回应对应持久停点并进入后续正文、证据和记忆。D022三调用及旧流程恢复保持兼容。


## D024：正文与独立多轮对话阶段（OP-20260913-019）

用户明确要求正文生成中暂停并进入独立NPC交流，替代D023中整轮提交后单次回应的安排。问话停点在记忆/摘要之前持久保存并释放锁；主角输入只触发NPC消息，结束才整理并自动接续正文。界面关闭、刷新和用户沉默都不视为对话结束。

NPC新增说法只能按角色陈述进入记忆，不能自动成为旁白事实。采用对话版本、消息回执、模型结果先保存与确定性后续ID保证重复请求/中断不重复推进。旧pipeline恢复兼容，真实模型知识边界仍须持续评审。
