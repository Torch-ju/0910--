## 1. 产品概述

用户进入一个具有明确背景和初始状态的故事世界，通过自然语言描述角色的行动。AI 根据行动、当前世界状态和已发生的剧情，生成下一段故事，呈现行动结果，并更新相关状态。用户继续输入行动，使剧情在持续互动中发展。

**核心体验：我做出行动，世界给出合理反馈；过去的选择会影响未来，而且故事始终记得这些选择。**

核心循环：

> 了解当前处境 → 输入行动 → 判断可行性 → 生成行动结果与剧情 → 更新世界状态 → 做出下一次行动。

### 1.1 用户问题

- 固定选项难以表达用户真正想做的事，自由探索受限。
- 普通对话容易遗忘物品、地点、人物关系和之前的承诺。
- 故事看似不断延续，但用户的行动没有实质影响。
- AI 容易替玩家作决定，或直接跳过玩家想参与的关键过程。
- 长篇剧情容易出现人物性格变化、重复事件和设定冲突。

### 1.2 产品目标

1. 用户能够自由描述行动，无需学习命令或提示词。
2. 每次有效行动获得与当前处境相符的反馈。
3. 物品、人物关系、任务和重要事件能被可靠保留并影响后续剧情。
4. 生成故事有推进、有悬念，同时保留用户的决策权。
5. 用户离开后能够恢复至最后一个完整回合并继续故事。

### 1.3 首版成功体验

用户完成开场后，至少连续参与 5 个回合；其中一次行动改变了可见世界状态，后续剧情能准确引用这个变化。用户关闭页面再打开后，仍能接着进行下一回合。

## 2. 产品范围与假设

### 2.1 首版默认方案

- 单人扮演一个主角，AI 扮演环境、配角和叙事者。
- 以中文文字故事为主，兼容手机与桌面浏览器。
- 提供 3 个经过检查的故事开场，覆盖奇幻冒险、悬疑调查、日常关系三个方向。
- 用户可填写主角名称与一句性格描述；初始世界规则由故事模板给定。
- 支持自由输入行动，同时提供 2～3 个可点击的行动建议。
- 同一会话顺序处理回合；每个回合只提交一次世界状态更新。
- 首版提供当前浏览器的匿名会话续玩，不要求注册；跨设备恢复后续支持。
- 支持多个故事存档，每个存档保留一条正式剧情时间线。

### 2.2 范围与优先级

| 能力 | P0 首版 | P1 后续 | P2 探索 |
| --- | --- | --- | --- |
| 故事开局 | 预设世界、主角命名、开场剧情 | 用户自定义背景和世界规则 | 世界模板创作与分享 |
| 互动方式 | 自由行动、建议行动、必要澄清 | 叙事风格与篇幅偏好 | 语音互动 |
| 世界状态 | 地点、时间、角色、物品、关系、任务、关键标记 | 更丰富的技能与资源体系 | 多角色共同控制 |
| 历史记忆 | 完整回合、事件记录、阶段摘要 | 用户可见的剧情回顾与搜索 | 多时间线对照 |
| 剧情控制 | 合理结果、后果反馈、关键决定交还用户 | 回退回合、分支存档 | 多人共同参与 |
| 保存恢复 | 自动保存、存档列表、继续故事 | 账号与跨设备同步、导出 | 社区分发 |
| 内容形式 | 文本叙事与状态面板 | 场景插画 | 动态漫画、音频演出 |

P0 不建设复杂战斗数值、经济模拟或完整开放世界系统。需要这些规则的故事模板应缩小为首版能够表达的范围。

## 3. 用户与使用场景

| 用户类型 | 主要诉求 | 典型场景 |
| --- | --- | --- |
| 轻度故事体验者 | 快速进入剧情，不知道下一步时有人引导 | 通勤时用 10 分钟体验几个回合 |
| 自由探索者 | 尝试预设选项之外的行动，观察不同后果 | 放弃任务路线，转而调查可疑配角 |
| 角色扮演爱好者 | 保持角色身份与人际关系的连续性 | 遵守之前的承诺，逐步取得某角色信任 |
| 剧情创作者 | 通过行动探索人物动机与情节可能性 | 尝试不同处理方式，寻找自然的故事转折 |

### 3.1 核心用户故事

- 作为新用户，我希望选择一个感兴趣的世界，快速知道自己是谁、在哪里、当前面临什么。
- 作为玩家，我希望输入“绕到后门观察”，而不仅仅选择系统给出的几个按钮。
- 作为玩家，我希望失去的钥匙不能再次使用，帮助过的人会记得我的行为。
- 作为玩家，我希望不可能完成的行动得到合理解释，而不是被 AI 强行判定成功。
- 作为玩家，我希望关键选择由自己做出，AI 不会擅自让我背叛朋友或接受任务。
- 作为回访用户，我希望继续最后完成的剧情，不必重新描述整个故事。

## 4. 核心用户流程

### 4.1 首次进入

1. 用户打开故事列表，查看题材、世界简介和预计体验风格。
2. 选择故事模板，填写主角名称与可选性格描述。
3. 系统创建存档，初始化世界状态和开场剧情。
4. 开场说明身份、地点、眼前事件和可行动对象。
5. 用户在行动输入框中开始第一回合，或点击一条行动建议。

**开场要求：**避免一次铺陈大量设定；用户读完后应能回答“我在哪里、现在发生了什么、我能做什么”。

### 4.2 常规回合

1. 用户输入行动，或点击建议将其填入输入框。
2. 点击“采取行动”提交；建议行动也须经过这一提交步骤。
3. 系统锁定当前状态版本，判断行动对象、条件和意图是否明确。
4. 如存在重大歧义，返回澄清问题；如可以处理，进入剧情生成。
5. 系统生成候选剧情、行动结果、状态变化和后续建议。
6. 通过一致性检查后，保存回合并更新世界状态。
7. 页面显示正式剧情、关键变化和新的行动建议。
8. 用户继续输入下一次行动。

### 4.3 暂停与续玩

1. 每个完整回合提交成功后自动保存。
2. 用户在存档列表中查看故事名、最近剧情摘要和更新时间。
3. 点击“继续故事”，恢复最后一个完整回合及其世界状态。
4. 如果上次离开时正在生成，先查询原回合结果，再决定显示完成内容或提供重试。

### 4.4 阶段结束

- 任务完成、角色死亡或故事达到预设收束条件时，可以进入阶段结局。
- 结局必须由已发生的事件和世界规则支撑，不以回合数作为唯一依据。
- 页面说明结局及关键行动的影响，并提供“返回存档”或“开始新故事”。
- 已结束存档可回顾；首版不在结局后自动续写或重置角色状态。

## 5. 功能需求

### 5.1 故事开局与存档（FR-01，P0）

**输入：**故事模板、主角名、可选性格描述。

**输出：**唯一存档、初始状态、开场剧情。

规则：

- 故事模板定义世界基础规则、初始地点、登场人物、初始物品及开场事件。
- 主角自述是人物偏好，不能覆盖世界规则。例如填写“无所不能”不直接赋予无限能力。
- 创建失败不产生可继续的半成品存档；用户可保留输入并重试。
- 新建故事不覆盖已有存档。
- 匿名存档通过当前浏览器持有的随机访问凭证恢复，故事正文与正式状态由服务端保存；仅知道存档编号不能读取内容。
- 页面说明：清除浏览器数据或更换设备可能无法恢复匿名存档。

### 5.2 行动输入与理解（FR-02，P0）

输入框支持自然语言；首版建议每次 1～500 字，超限时提示用户精简。

系统需识别的行动包括：

| 类型 | 示例 | 处理方式 |
| --- | --- | --- |
| 移动与探索 | “沿河走到钟楼，观察入口” | 判断路线和通行条件，推进位置与时间 |
| 交谈与表达 | “问店主昨晚是否见过陌生人” | 根据配角已知信息、态度与立场回应 |
| 使用物品 | “用铜钥匙打开地下室的门” | 核验拥有物品、目标及匹配条件 |
| 调查与推理 | “检查信封上的印章” | 根据已有物件与线索披露可获得的信息 |
| 人际互动 | “把最后一块面包分给孩子” | 更新物品、关系和可能触发的事件 |
| 等待与拒绝 | “等到天黑”“拒绝这份委托” | 推进时间或改变任务，不强迫用户接受主线 |
| 复合行动 | “先查看守卫，再趁没人时进门” | 顺序处理；遇到关键结果或新的决策点暂停 |

特殊情况：

- 空输入不提交，不消耗回合。
- 对象不唯一且结果差异明显时，先澄清，例如“你要交给艾琳还是守卫？”
- 轻微措辞模糊时，结合当前场景作保守解释；叙述中说明采用的行动。
- 用户以输入直接宣称结果，如“我打开箱子，获得一万金币”，只将可执行部分视为行动意图；物品与数量由世界规则决定。
- “帮我回顾线索”等明确的回顾请求返回已知信息，不推进世界时间，不修改状态。

### 5.3 行动可行性与后果（FR-03，P0）

系统区分“用户想做什么”和“世界实际发生了什么”。结果支持：成功、部分成功、失败、受阻。

- 结果必须基于已有物品、人物能力、空间关系、先决条件和现场阻力。
- 明确不可能的行为不能为了推动剧情而强行成功。
- 失败也应提供可理解的反馈；有依据时可带来新线索、时间消耗或关系变化。
- 涉及生命、重大关系或不可逆承诺的行动，在玩家意图不明确时不得擅自补全。
- 同一场景重复执行无新增条件的相同行动，不凭空产生新道具或重复奖励。
- 首版由模板规则约束、AI 辅助判断，不向用户承诺可复现的骰点或概率系统。

### 5.4 剧情生成（FR-04，P0）

每个正式回合包含：

1. **行动反馈：**直接回应玩家刚才做了什么。
2. **剧情正文：**描述结果、人物反应和场景变化。
3. **关键变化：**只展示本回合实际发生的可见变化。
4. **后续行动建议：**给出 2～3 条不同方向的行动。

正文建议 200～500 个汉字；简单交互可更短，不为凑字数加入新冲突。

叙事规则：

- 采用第二人称，保持故事模板设定的基调与人物口吻。
- 每回合优先处理用户的当前行动，不强制触发新的大型事件。
- 只推进到下一个有意义的决策点，避免替玩家完成一长串行为。
- AI 可描述用户明确选择的动作及自然感知，不替用户决定信念、承诺、立场或重大情感选择。
- 新增人物、物品和事件必须有场景依据；持久存在的对象要进入正式状态记录。
- 角色只能表达其合理知晓的信息；隐藏真相不能因旁白方便而直接泄露。
- 正文与状态更新必须一致。例如正文“你把面包递给孩子”，库存应减少；若没有递出，不应扣除。

### 5.5 世界状态（FR-05，P0）

状态分为可供玩家查看的信息与尚未发现的内部信息；服务端按可见性返回，不依赖前端隐藏。

| 状态维度 | 示例字段 | 规则 |
| --- | --- | --- |
| 世界规则 | 魔法限制、昼夜规则、区域规则 | 由模板定义，普通行动不能直接重写 |
| 时空 | 当前地点、日期、时段、经过时间 | 移动与等待导致的时间变化保持连续 |
| 主角 | 身份、身体状况、已知能力 | 状态变化须由事件支撑 |
| 配角 | 人物 ID、位置、状态、已知信息 | 名称可以相似，身份必须独立 |
| 物品 | 物品 ID、持有者、数量、属性 | 不允许负库存、重复持有唯一物品 |
| 关系 | 双方 ID、关系描述、影响事件 | 变化有依据，不因单轮措辞突然反转 |
| 任务 | 目标、当前阶段、完成条件 | 先决条件未满足时不能直接完成 |
| 事实与标记 | 门已解锁、信件已读、承诺已作出 | 已确定事实不能被后续无理由覆盖 |
| 隐藏信息 | 未知动机、待触发事件、未发现线索 | 只有满足发现条件后才能变为玩家已知 |

状态面板优先展示当前地点、角色状态、背包、活跃任务和已发现线索。关系变化以文字为主，首版不暴露精确好感度。

### 5.6 历史记忆与连续性（FR-06，P0）

记忆采用三层组织：

| 层级 | 保存内容 | 用途 |
| --- | --- | --- |
| 最近回合 | 最近若干回合的原文与行动 | 保持当前对话、动作和场景衔接 |
| 剧情摘要 | 较早阶段的关键经过、人物动机和未解问题 | 在有限上下文中保留长期脉络 |
| 结构化事实与事件 | 物品转移、任务变化、承诺、人物状态等 | 作为状态判断和历史核验的依据 |

要求：

- 完整回合记录持久保存，不因生成摘要而删除原文。
- 摘要保存其覆盖的回合范围和版本，可追溯到原始事件。
- 组装生成上下文时，优先纳入与本次行动涉及的人物、地点、物品和任务相关的记忆。
- 重要承诺、唯一物品、角色死亡、任务完成等事实不得只存在于摘要中。
- 新回合不能把已经明确的事实当成尚未发生，除非剧情中存在明确的新事件改变它。
- 摘要与正式状态发生冲突时，以已提交事件及其对应状态为准，并修复摘要。
- 历史事件自身发生矛盾时，不通过临时编故事掩盖；暂停本次提交，保留旧状态并进入错误恢复。

### 5.7 行动建议（FR-07，P0）

- 生成 2～3 条简短、明确、当前可尝试的行动。
- 建议应体现不同意图，如观察、交谈、直接行动，而不是相同选择的不同措辞。
- 建议不得泄露隐藏真相、确定未知成功结果，或要求玩家使用未持有的物品。
- 点击建议只填入输入框，允许用户修改后提交。
- 用户始终可以输入其他行动；建议不构成可行行为的白名单。

### 5.8 回合保存与并发控制（FR-08，P0）

- 每次提交携带唯一请求 ID，以及用户当前看到的状态版本。
- 同一请求 ID 的重复提交返回同一回合结果，不再次推进剧情或发放奖励。
- 同一存档同时只允许一个写回合；生成期间禁止再次提交行动，输入草稿仍可编辑。
- 另一个标签页基于旧版本提交时，提示刷新至最新剧情，不强行覆盖。
- 剧情正文、结构化事件、状态更新和回合编号作为一个整体提交。
- 网络中断或客户端刷新不被视为用户发起了新回合；恢复时先查询原请求状态。
- 摘要可在回合提交后更新。摘要更新失败时保留已完成回合，并在下次生成前补齐必要记忆。

## 6. 页面与交互

### 6.1 页面结构

| 页面 | 核心内容 | 主要操作 |
| --- | --- | --- |
| 故事 / 存档页 | 故事模板、我的存档、最近进展 | 新建故事、继续故事、查看结局 |
| 开局设置页 | 世界简介、主角名、性格描述 | 开始故事、返回 |
| 剧情页 | 连续剧情、行动输入、建议、可见状态 | 采取行动、查看状态、返回存档 |
| 阶段结局视图 | 结局、关键选择与影响 | 回顾剧情、开始新故事 |

### 6.2 剧情页布局

- 顶部：故事名、当前章节或地点、保存状态。
- 主区域：按时间排列的玩家行动与正式剧情回合。
- 侧边状态面板：当前地点、主角状态、背包、任务和线索。
- 底部：行动建议、输入框、提交按钮。
- 手机端将状态面板收纳为可展开区域，输入区保持容易访问。

### 6.3 界面状态

| 状态 | 用户看到什么 | 可进行的操作 |
| --- | --- | --- |
| 等待行动 | 最近剧情、建议与输入框 | 编辑并提交行动 |
| 等待澄清 | 简短问题与明确对象 | 补充原行动，不产生正式回合 |
| 正在生成 | 进度提示，显示已提交行动 | 阅读历史、编辑下一步草稿 |
| 待校验 | “正在确认剧情与世界状态” | 阅读历史，暂不提交新行动 |
| 已完成 | 正式正文、状态变化、已保存提示 | 进行下一回合 |
| 生成失败 | 错误提示、原行动仍在 | 使用原请求重试或在确认失败后修改行动 |
| 状态已更新 | 另一页面已完成回合的提示 | 加载最新剧情后重新行动 |
| 故事结束 | 结局与回顾入口 | 回顾或新建故事 |

首版优先完整回合展示。若采用逐字流式显示，未通过校验的内容必须标识为“生成中”，不得作为已发生的事实或触发状态面板更新；校验失败后不能留下看似正式的半段剧情。

## 7. 生成与校验要求

### 7.1 输入上下文

每次生成至少包含：故事规则、主角设定、当前状态、玩家已知范围、最近回合、相关历史记忆、未解决的剧情线索，以及本次行动。

上下文长度超限时，应减少无关旧叙述，而不是截断关键事实或随机丢弃人物设定。具体回合窗口与预算由模型评测确定，不在 PRD 中固定模型或供应商。

### 7.2 生成结果结构

| 字段 | 含义 |
| --- | --- |
| `outcome` | 成功、部分成功、失败、受阻、需要澄清或回顾 |
| `narrative` | 玩家可见的正式剧情或澄清 / 回顾内容 |
| `events` | 本回合发生的可追溯事件，引用明确实体 ID |
| `state_changes` | 状态变更提案，包含目标、变更前提和变更内容 |
| `visible_changes` | 玩家有资格知道的状态变化 |
| `suggested_actions` | 2～3 个行动建议；结局时可为空 |
| `ending` | 是否达到阶段结局及原因 |

AI 返回的是候选结果。正式回合编号、请求状态与状态版本由系统分配，不能由模型自行决定。

### 7.3 校验与提交

1. 检查结果结构、必要字段和实体引用。
2. 检查库存、唯一物品、任务先决条件、人物身份等确定性约束。
3. 检查正文是否与变更提案一致，是否擅自代替玩家做出关键选择。
4. 检查玩家可见内容及建议是否泄露隐藏信息。
5. 校验成功后，原子提交新回合及状态。
6. 校验失败时，携带具体冲突原因进行一次修复生成；仍失败则返回失败状态，不提交任何候选变更。

数值和引用约束应通过明确规则校验；叙事合理性检查不能被视为绝对正确，需要通过测试集和人工抽检持续评估。

## 8. 数据对象与状态模型

| 对象 | 关键内容 | 关系 |
| --- | --- | --- |
| 故事模板 | 世界规则、初始人物、初始状态、开场、结局条件 | 创建多个独立存档 |
| 存档 | 访问归属、模板版本、主角、当前状态版本、进行状态 | 包含一条正式回合序列 |
| 世界状态 | 实体、位置、关系、物品、任务和事实标记 | 由已提交事件逐步更新 |
| 行动请求 | 请求 ID、存档、基准版本、原始输入、处理状态 | 最多关联一个正式回合 |
| 剧情回合 | 行动、正文、事件、建议、前后状态版本 | 只包含已成功提交的结果 |
| 事件 | 涉及实体、发生回合、变化、玩家可见性 | 支撑状态恢复与历史核验 |
| 记忆摘要 | 覆盖范围、关键经过、事实引用、生成版本 | 辅助上下文组装，不替代正式记录 |

行动请求生命周期：

> 已接收 → 处理中 → 待校验 → 已提交。

分支：需要澄清时等待用户补充；生成或校验失败时记录失败原因。用户可见的失败状态必须与“仍在服务端处理中”区分，避免误导用户重复付费请求。

## 9. 示例回合

### 9.1 已知背景

- 地点：旧钟楼门外，傍晚。
- 主角持有一把铜钥匙、一盏油灯；铜钥匙为唯一物品。
- 门处于上锁状态。
- 历史事件：主角曾答应守塔人，不损坏钟楼内的物品。
- 内部事实：铜钥匙能够开启侧门；地下室还有一扇未被发现的门。

### 9.2 用户行动

> 我用铜钥匙打开侧门，举起油灯看看里面有什么。

### 9.3 期望剧情方向

> 铜钥匙在锁孔里卡了一下，随着你轻轻转动，门内传来一声低响。你推开侧门，油灯的光照亮狭窄的入口厅。守塔人让你别碰坏东西的叮嘱浮上心头。
>
> 桌面上摊着一本发黄的值班簿，通往楼上的木阶积着灰。你发现门内侧有几道新鲜擦痕。更深处暂时看不清。

### 9.4 正式变化

| 项目 | 回合前 | 回合后 |
| --- | --- | --- |
| 侧门 | 上锁 | 已打开 |
| 主角位置 | 门外 | 入口厅 |
| 铜钥匙 | 主角持有 1 把 | 仍持有 1 把 |
| 时间 | 傍晚 | 傍晚，经过少量时间 |
| 已知线索 | 无门内擦痕记录 | 发现门内侧的新鲜擦痕 |
| 历史承诺 | 不损坏钟楼物品 | 继续有效，未违背 |
| 地下室的门 | 未知 | 仍未知，不在建议中泄露 |

建议行动：“查看值班簿”“检查门内擦痕”“观察木阶是否安全”。

### 9.5 反例

- 钥匙未被消耗，却从背包消失。
- 主角未经选择就砸毁桌子，违背之前的承诺。
- 旁白直接揭示地下室的秘密入口。
- 下一回合把侧门重新描述为“从未被打开”。
- 重复提交同一行动后，在入口厅凭空再次发现另一把唯一铜钥匙。

## 10. 异常处理

| 情况 | 系统行为 | 用户反馈 |
| --- | --- | --- |
| 输入过长或为空 | 在提交前拦截 | 指明限制，保留输入 |
| 行动缺少必要对象 | 请求澄清，不推进状态 | 简短提问，让用户补充 |
| 行动在当前条件下不可能 | 生成受阻反馈，不伪造成功 | 解释障碍，给出可尝试方向 |
| AI 超时或暂不可用 | 保留旧状态和原请求 | 显示失败或处理中，允许查询结果 |
| 输出结构不合法 | 尝试一次修复，失败则结束请求 | 提示重试，不展示错误状态变更 |
| 正文与状态冲突 | 阻止提交并尝试修复 | 保留最后完整回合 |
| 保存失败 | 不宣告回合完成；按同一请求重试提交 | 提示暂未保存，避免继续推进 |
| 多标签页冲突 | 拒绝旧版本写入 | 提示加载新回合 |
| 摘要缺失或过期 | 使用相关原始事件补齐或重新构建 | 需要等待时显示准确状态 |
| 会话凭证失效 | 不返回其他用户存档 | 说明无法访问当前存档 |

## 11. 非功能要求

### 11.1 性能与成本

以下为首版候选目标，需在选定模型、网络环境与测试负载后验证：

- 提交后 1 秒内出现明确的处理中反馈。
- 普通回合完成并保存的 P95 时延目标为 20 秒以内；超过目标继续准确显示状态。
- 超时阈值、单回合生成预算和并发上限应可配置。
- 监控每回合上下文长度、生成长度、耗时、修复次数和模型调用成本。
- 仅用与本次行动有关的历史内容组装上下文，避免每轮重复传入完整长篇剧情。

### 11.2 可靠性与访问边界

- 已完成回合在刷新、断网恢复和服务重启后可恢复。
- 双击、重试、重复回调不得导致重复回合或状态累加。
- 存档访问须校验归属；隐藏世界信息不得随前端接口完整下发。
- 诊断日志默认记录请求 ID、耗时和错误类别，避免无必要地复制完整剧情或凭证。
- 模型返回内容按文本呈现，不作为可执行代码运行。

### 11.3 可用性

- 所有主要操作可通过键盘完成。
- 中文输入法组合输入期间，回车不应误提交；提供明确的提交按钮。
- 状态变化不能只依赖颜色表达。
- 加载、保存中、已保存和失败状态需有可读文字。
- 用户阅读历史时，新内容不强制把页面滚动到底部。

## 12. 指标与埋点

### 12.1 核心指标

**核心体验指标：每个已开局存档的有效连续互动回合数。**

有效回合指：玩家主动提交行动、系统提交完整剧情及状态、非澄清 / 回顾 / 重试副本。它用于衡量参与程度，不单独代表故事质量，应结合用户反馈判断。

| 指标 | 口径 | 用途 |
| --- | --- | --- |
| 开局转化率 | 完成首个有效回合的用户 / 进入开场的用户 | 观察是否容易开始 |
| 5 回合完成率 | 完成至少 5 个有效回合的存档 / 已完成首回合的存档 | 观察早期持续参与 |
| 续玩率 | 后续自然日再次产生有效回合的存档 / 可观察完整窗口的活跃存档 | 观察长期吸引力 |
| 自由行动占比 | 非直接采纳建议的有效行动 / 总有效行动 | 观察自由表达价值，不作为越高越好的目标 |
| 生成成功率 | 提交成功的行动请求 / 可处理的行动请求 | 观察服务稳定性 |
| 一致性通过率 | 抽检中无关键事实冲突的回合 / 抽检回合 | 观察记忆与状态质量 |
| 重试与修复率 | 发生重试或修复的请求 / 总请求 | 定位可靠性与成本问题 |
| 用户反馈 | 对剧情、行动反馈和连贯性的评价 | 补充回合数无法表达的体验质量 |

### 12.2 最小埋点

记录 `story_started`、`action_submitted`、`clarification_requested`、`turn_committed`、`turn_failed`、`suggestion_selected`、`save_resumed`、`ending_reached`。

关联存档、请求、回合和模型配置版本；埋点统计不默认采集用户输入全文。

## 13. 验收标准

下列用例均为首版发布前必须通过的 P0 检查。涉及生成质量的用例使用固定测试场景、明确判定标准和人工复核，不以单次主观“感觉合理”通过。

| 编号 | 场景 | 验收要求 |
| --- | --- | --- |
| AC-01 | 完成开局 | 正确建立角色、初始状态与开场；用户可立即行动 |
| AC-02 | 输入建议之外的合法行动 | 能理解并回应，不要求用户必须选择建议 |
| AC-03 | 目标不明确 | 先澄清；澄清前回合数、时间和物品不变 |
| AC-04 | 使用未持有的物品 | 不判定为已使用，不凭空补发物品 |
| AC-05 | 合法转移唯一物品 | 原持有者失去物品，接收者获得物品，无复制 |
| AC-06 | 用户直接宣称获得奖励 | 根据实际行动与规则判断，不直接接受其状态宣称 |
| AC-07 | 历史承诺影响剧情 | 在相关后续场景中保留并体现承诺，不无理由遗忘 |
| AC-08 | 连续 30 回合 | 人物身份、关键物品和任务阶段保持一致，摘要可追溯 |
| AC-09 | AI 替玩家作重大决定 | 检查阻止提交或修复，最终输出把决定留给玩家 |
| AC-10 | 隐藏事实未被发现 | 正文、建议和状态接口均不泄露该事实 |
| AC-11 | 双击提交及同请求重试 | 仅产生一个正式回合和一次状态变化 |
| AC-12 | 两个标签页同时提交 | 只提交一个基于有效版本的回合，另一个收到版本冲突 |
| AC-13 | 生成或校验失败 | 保留旧状态，不出现半完成回合；原行动可恢复 |
| AC-14 | 保存失败后重试 | 最终最多提交一次；未保存前不显示已完成 |
| AC-15 | 刷新页面及服务重启 | 恢复最近完整回合；处理中请求先查询原结果 |
| AC-16 | 回顾历史请求 | 准确返回已知事实，不推进时间或改变关系 |
| AC-17 | 正文与状态一致 | 正文描述的持久变化均有对应记录，记录无正文未发生的变化 |
| AC-18 | 非存档持有者访问 | 无法读取剧情、世界状态或修改存档 |
| AC-19 | 阶段结局 | 有可追溯的触发条件，保存结局，不自动重开剧情 |
| AC-20 | 手机与中文输入 | 无主要内容遮挡，输入法回车不误提交，主流程可完成 |

## 14. 实施里程碑

以下按成果划分，不预估未确认团队规模下的交付日期。

| 阶段 | 交付物 | 进入下一阶段的条件 |
| --- | --- | --- |
| M1：叙事规则验证 | 3 个开场模板、状态字段、测试剧情与结果样例 | 用人工样例跑通行动、结果与状态变化 |
| M2：完整回合闭环 | 开局、行动输入、生成、校验、提交、状态面板 | 单存档完成连续 5 回合，失败不污染状态 |
| M3：记忆与恢复 | 历史事件、摘要、存档恢复、幂等与并发控制 | 通过长回合、断线恢复、重复提交测试 |
| M4：首版试用 | 移动端完善、基础埋点、异常提示、质量评测 | P0 验收通过，已知问题与运营预算明确 |

## 15. 待确认事项

这些问题不阻止按本文默认方案制作原型，但应在正式研发排期前确认：

1. **目标用户与主打题材：**先服务休闲阅读用户，还是重度角色扮演用户？首批模板据此调整。
2. **世界控制权：**是否需要用户自由创建世界，还是首版先验证预设世界中的行动体验？
3. **剧情风格：**更强调文学叙事、游戏挑战，还是角色关系？这会影响评价标准。
4. **存档要求：**当前浏览器续玩是否足够，账号与跨设备同步是否需要提前至 P0？
5. **预算与体验取舍：**可接受的回合等待时间、日使用量和单用户成本是多少？
6. **与现有漫想的关系：**作为独立文字互动入口，还是后续将每段剧情转为漫画分镜？本文默认先完成文字互动闭环。

---

**本版评审重点：**先确认“玩家行动能产生可信后果、历史能被记住、状态能持续恢复”这三项核心体验，再扩展表现形式和玩法复杂度。
