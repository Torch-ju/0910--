## 1. 产品形态判断

- **产品类型与核心任务**：对话式写作陪伴助手，帮助用户从想法推进到完整故事；用户保留故事决定权。
- **核心交互**：多轮对话、候选建议、用户采用或修改、分阶段成果整理、恢复创作。
- **开发路径**：纵向切片。引导是否有效、是否尊重用户决定，必须在真实交互中验证。
- **目标终端**：按通用手册默认先做 Web。本地阶段仅绑定回环地址，不因没有登录而开放公网。
- **当前建议阶段**：第 1 阶段实现“建立项目 → 引导对话 → 提出候选设定 → 用户采用/拒绝 → 保存 → 刷新或重启后恢复”。同时验证跳过、修改和导出已有资料。
- **完整产品方向**：后续覆盖故事方案、分章纲要、逐章正文与修订。第 1 阶段可用不等于整部故事创作功能已交付。
- **范围边界**：首版发布是否包含全部正文功能仍未确认；当前按阶段拆分，不将拆分解释为取消需求。

## 2. 采用的默认方案

| 方案 | 采用原因与实施条件 |
| --- | --- |
| Python 3.11.x、项目独立虚拟环境 | 遵循手册后端基线；当前 PATH 未发现该版本，开发前准备，不替换系统 Python |
| FastAPI + Pydantic | 提供独立可验证的 API，并校验请求、模型产出及响应 |
| pytest | 离线验证状态流转、解析、错误和恢复逻辑 |
| Next.js App Router + TypeScript + Tailwind CSS | 使用正式 Web 技术完成最小交互切片，后续复用；不另建平行临时页面 |
| npm、依赖锁文件、ESLint、TypeScript 检查 | 保持依赖可复现并检查界面工程质量 |
| Git | 实现前初始化并先配置忽略规则；当前文档生成不初始化仓库 |
| `/api/v1` | 统一业务 API 前缀，前端经 API 使用后端能力 |
| 模型服务适配层 | 通过官方 SDK 或核验过的兼容接口调用；模型与 Prompt 不散落在页面和路由中 |
| 代码控制状态转换 | 模型负责建议，代码负责合法写入、版本检查与恢复 |

模型厂商和型号尚未确定。本轮不虚构可用模型、价格或调用效果；开发可先完成 mock，真实验收前须确定模型、数据处理接受范围及成本限额。

## 3. 触发的按需模块

| 模块 | 触发需求 | 引入阶段 |
| --- | --- | --- |
| SQLite + SQLAlchemy + Alembic | 项目、消息、建议、版本、任务之间有关联；采用设定须事务写入 | 第 1 阶段 |
| SSE + 持久化生成任务与事件 | 对话需要逐步显示，断线需要恢复，失败需要明确收尾 | 第 1 阶段 |
| Playwright 关键交互测试 | 必须验证采用、拒绝、刷新和恢复等真实界面行为 | 第 1 阶段 |
| Markdown 导出 | PRD 要求资料可带走；首阶段仅导出已有资料 | 第 1 阶段 |
| 项目内资料筛选、分层摘要 | 长对话不能一直全量发送，且不能遗忘正式决定 | 第 1 阶段建立边界，第 2—3 阶段扩展 |
| 章节版本与变更影响分析 | 正文协作、局部采用、修订不能覆盖原稿 | 第 3 阶段 |

SQLite 用于本地单进程、低写入并发验证；它每个数据库同时只有一个写入者。多人并发或多实例部署前评估 PostgreSQL，不将 SQLite 文件放到多实例共享网络盘上。[SQLite 官方适用说明](https://www.sqlite.org/whentouse.html)

| 正式视觉系统 | 最小界面优先保留加载、错误、恢复及确认交互 | 核心链路通过后读取前端手册，继续完善已有界面 |

向量库、RAG 框架、OCR、Word/PDF 处理、对象存储、Redis、任务队列、动态工具规划和微服务均未被第 1 阶段需求触发，不预装。出现明确规模或功能需求时再评估。
