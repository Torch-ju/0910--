# 写作陪伴助手 PRD

版本：v0.1 草案  
日期：2026-09-11  
状态：产品需求讨论稿，未确认项不视为用户决定

## 1. 产品定位

一个通过对话持续引导用户构思、规划、写作和修订故事的写作陪伴助手。产品负责组织过程、发现缺口、提出建议、记录决定；用户掌握故事的创作决定权。

首个创作方法来源为 jin-yong-perspective，用于支持武侠题材的人物成长、江湖关系、价值冲突、武学规则与伏笔设计。该技能是引导方法的一种来源，不意味着用户必须模仿某位作者、采用固定情节或接受系统提出的设定。

本 PRD 描述要建设的产品；当前对话用于明确产品需求，不直接替未来用户决定故事。

## 2. 已确认需求与待定边界

### 已确认

- 产品形态是写作陪伴助手，需要项目本身提供引导。
- 通过对话帮助用户逐步完成整个故事。
- 故事内容与关键选择由用户决定。
- 先完成 PRD，再推进实现方案。
- 使用提供的 jin-yong-perspective 技能作为创作方法来源。

### 尚待产品负责人决定

- 首发载体：网页、桌面应用或其他形式。
- 首发题材：仅武侠，或允许其他题材。
- “完成整个故事”的首版验收范围：完整故事方案，或包含逐章正文与修订。
- 《技术可行性手册》指本产品的工程实施文档，还是产品内向创作者提供的交付物；不能直接等同于故事创作手册。
- 数据保存、账号、跨设备使用及模型接入方式。

下文为建议的产品行为，供讨论与确认，不代表以上选项已确定。

## 3. 用户与核心需求

主要服务于有写作意愿，但难以把想法推进成完整故事的个人创作者。用户可能只有一个画面，也可能已有角色、梗概或部分正文。

用户需要：

1. 知道当前最值得解决的问题，减少面对空白页面时的负担。
2. 在没有想法时获得具体启发，在有明确想法时保留自己的方向。
3. 看见零散对话如何积累为可继续写作的故事资料。
4. 暂停后能够找回进度，修改设定后能够识别受影响的内容。
5. 获得反馈与写作协助，并决定哪些内容成为正式版本。

## 4. 核心体验原则

### 用户拥有决定权

系统提出的角色、背景、冲突、结局和正文均先作为建议或草稿。只有用户明确接受的内容才能进入已确认设定。用户沉默、跳过或离开，不代表接受。

用户可以授权助手在指定范围内发挥，例如“给这个场景写三种开头”。这份授权只覆盖当前范围，不能推导成允许助手决定整部作品的走向。

### 引导应随用户变化

每轮聚焦一至两个有价值的问题。用户可以自由回答、请求示例、跳过、返回修改，或指定先处理某一部分。流程提供方向，不强制用户依次填完表单。

### 创作有积累，建议有出处

界面区分用户原话、助手建议和已确认设定。助手解释建议时连接具体创作问题，例如“这个选择能让反派与主角的目标发生冲突”，而不是仅报出技能术语。

### 技能服务创作

技能中的模板可被调整或拒绝。产品不将角色扮演当作真实作者身份，不把技能中的文学解读或历史说法直接当成已核实事实。

## 5. 端到端用户旅程

| 阶段 | 产品如何引导 | 用户决定什么 | 累积成果 |
| --- | --- | --- | --- |
| 开始项目 | 询问创作目标、现有材料和希望获得的帮助 | 写什么、从哪里开始、陪伴方式 | 项目简述 |
| 找到故事核心 | 从画面、人物或矛盾切入；没有想法时给少量候选 | 核心人物、愿望与冲突 | 故事种子与一句话梗概 |
| 建立故事基础 | 追问背景、人物动机、关系与规则缺口 | 时代、世界边界、人物与重要关系 | 世界设定、人物档案 |
| 搭建完整情节 | 推演不同选择的后果，检查起承转合 | 关键事件、转折、高潮和结局 | 完整梗概、人物成长线 |
| 制定写作计划 | 拆分章节或场景，安排伏笔与节奏 | 篇幅、章节目标、叙述方式 | 分章纲要、伏笔表 |
| 陪伴正文写作 | 提供场景提示、局部起草和反馈 | 写法、措辞、哪些草稿采用 | 章节正文 |
| 检查与修订 | 标出矛盾、缺失动机和未兑现伏笔，提出修订建议 | 修改范围与最终取舍 | 修订稿、检查记录 |
| 完成与导出 | 汇总成果及仍未解决的问题 | 是否完成、导出哪些内容 | 可导出的故事资料或完整作品 |

用户可从任意已有材料开始。阶段完成依据是所需成果是否具备以及用户意愿，不依据固定对话轮数。正文写作是否纳入首版，仍需确认。

## 6. 功能需求

### F1 项目建立与恢复

- 支持新建、命名并继续已有故事项目。
- 支持用户粘贴现有想法、梗概或正文，先生成理解摘要供纠正。
- 恢复项目时显示最近进展、未决事项与建议下一步。
- 不同项目的设定与对话不得相互混用。

### F2 对话引导

- 根据已有资料识别当前缺口，提出下一步问题。
- 有想法的用户可以直接描述；没想法的用户可以请求示例或候选方向。
- 提供“给我启发”“继续深挖”“先跳过”“回到前面”等操作，并接受等价自然语言。
- 每轮建议应具体到当前故事，避免连续重复询问已有答案。
- 对偏离当前阶段但属于该故事的新想法，先记录，再帮助用户决定是否转向。

### F3 决策记录与确认

- 区分待讨论、已确认、已撤回三类决定。
- 用户明确表达“就用这个”等接受意图时，可直接记录，无须重复确认。
- 对“都不错”“以后再说”等模糊回复，不自动选择方案。
- 将助手新推导的关键设定展示为候选，支持逐项或整组采用。
- 支持撤回和修改已确认决定，并保留此前版本。

### F4 故事资料工作区

- 对话旁可查看项目概览、世界设定、人物关系、情节纲要、章节、伏笔与未决事项。
- 资料由对话逐步形成，用户也能直接编辑。
- 已确认资料与待采用草稿在视觉上明确区分。
- 每项关键设定可追溯到相关对话或用户编辑。

### F5 一致性与变更影响

- 对人物动机、时间线、世界规则、章节事件及伏笔进行一致性检查。
- 发现矛盾时说明冲突在哪里，给出可选处理方式。
- 修改关键设定后，列出可能受影响的章节与关系，不自动覆盖已确认正文。
- 将有意保留的悬念与真正遗漏区分开；判断不清时交由用户决定。

### F6 写作协作

- 支持用户自行写作后获取反馈，以及按用户要求生成局部草稿。
- 草稿引用当前已确认设定；新增关键设定须显式标出。
- 允许局部采用、修改或丢弃草稿，保留用户原稿。
- 每章写作前能查看该章目标、涉及人物、冲突与待回收伏笔。
- 本功能属于完整产品范围，是否为首版必需项待确认。

### F7 成果导出

- 支持预览并选择导出项目资料、完整梗概、分章纲要及已有正文。
- 导出内容明确区分已确认成果与待定问题。
- 首版建议支持 Markdown；其他文档格式按需求确定。
- 《技术可行性手册》的位置与内容，在其用途确认后另行定义。

### F8 创作方法接入

- 将 jin-yong-perspective 转化为适时出现的引导问题与检查维度。
- 支持人物的欲望、恐惧、缺点、选择及后果分析。
- 支持历史与虚构边界、武学限制、势力关系、伏笔安排的讨论。
- 不强制百章结构、单一英雄成长路线、固定爱情模式或特定结局。
- 对涉及真实历史的内容，区分已核实信息、待考证信息与虚构设定；考证能力的实现方式留待技术方案确定。

## 7. 建议的信息布局

主工作区包含三个部分：

- 项目导航：阶段进度、已有成果与未决事项。
- 对话区域：当前问题、用户表达与助手建议。
- 故事资料区域：当前讨论涉及的设定或草稿，可编辑、采用和查看变更。

布局需要适配最终载体。进度以成果状态呈现，例如“人物动机待补充”，不使用没有依据的完成百分比。

## 8. 建议首版范围

建议首先交付从故事种子到完整梗概、人物设定和分章纲要的可用闭环，同时支持资料保存、恢复、修改与导出。它可以验证产品能否持续引导用户并保留创作决定权。

该建议尚未确认。如果首版目标是陪伴完成整部正文，章节编辑、草稿版本、长篇上下文管理与全文一致性检查须同时纳入首版验收，不能仅交付大纲后宣称完成整个故事。

暂不建议首版包含多人实时协作、作品社区、商业发布、收费体系及大量技能市场功能，除非后续明确需要。

## 9. 验收场景

| 场景 | 预期行为 |
| --- | --- |
| 用户只有一个模糊画面 | 助手从画面提出具体问题，帮助形成故事种子，不要求先填写完整设定 |
| 用户完全没有方向 | 提供少量可理解的故事方向，等待用户选择或修改 |
| 用户拒绝全部建议 | 保留拒绝结果，换角度引导，不将任何候选写入正式设定 |
| 用户只说“都挺好” | 保持待定，不代选 |
| 用户明确说“用第二个” | 采用对应方案并继续推进，不反复要求确认 |
| 用户更改主角身份 | 更新决定记录，展示可能受影响的关系和章节 |
| 用户中途离开后回来 | 恢复已有成果、最近决定及待解决问题 |
| 用户要求先写某个场景 | 允许跳转，使用已有设定，标出必要的临时假设 |
| 长对话中出现矛盾 | 指出具体冲突并请求用户取舍，保留原有版本 |
| 用户导出故事方案 | 输出结构完整且与已确认设定一致的文件，列出尚未解决的事项 |

## 10. 质量要求与验证方向

- 可靠保存：展示保存状态；生成失败不应丢失用户输入或已有资料。
- 过程可恢复：对话中断后可继续；长对话摘要不能悄悄改变用户决定。
- 可控生成：支持停止生成和重试，失败原因以可理解的方式提示。
- 数据边界：明确内容保存位置及模型处理方式；故事不默认公开，删除和导出规则在实现前明确。
- 创作质量：通过完整体验测试判断问题是否有帮助、建议是否贴合故事、用户能否持续推进。
- 决策准确性：检查是否出现未授权设定进入正式资料、拒绝被忽略或旧决定覆盖新决定。

待验证指标包括：从建立项目到形成首个已确认故事种子的完成率、从种子到完整梗概的完成率、恢复项目后的继续创作率，以及用户对掌控感与引导有效性的评价。当前不设未经验证的数值目标。

## 11. 下一轮产品决策

优先明确两个会影响交付范围的问题：

1. 首版是否必须覆盖逐章正文与修订，还是先完成故事方案及分章纲要？
2. 《技术可行性手册》是用于开发这个助手的工程文档，还是助手提供给创作者的某种成果？如果是后者，它具体要帮助创作者做什么判断？

明确这两点后，继续确定载体与保存方式，再整理功能优先级、用户流程和技术可行性方案。
