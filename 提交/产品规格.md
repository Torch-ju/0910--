# 活动报名与分组系统｜产品规格

| 项目 | 内容 |
|---|---|
| 文档版本 | v1.0.0 |
| 状态 | 开发评审稿 |
| 适用范围 | 单场 300 人技术活动；5 个能力方向；每方向 60 个正式名额 |
| 依据 | `材料/活动背景.md`、`材料/参与者画像.md`、`材料/历史反馈.md` |

> 口径说明：材料未规定的候补排序、转正方式与超额权限，本文以“建议基线”保证方案可执行，并在文末列为待澄清问题；确认后应改为活动正式规则。

## 目标与非目标

### 目标

1. 让参与者在一个流程内查看五个方向的实时余量，并且只能选择一个方向完成报名或进入候补。
2. 在无人工容量例外时，任一方向正式报名人数始终不超过 60 人，五个方向正式人数合计不超过 300 人；并发报名也必须满足该约束。
3. 每次报名操作都给出可核验结果：方向、状态（报名成功/候补/失败）、提交时间和报名编号，解决“不清楚报名是否成功”的反馈。
4. 报名截止后锁定参与者自助操作；自动候补转正按冻结规则执行，人工转正和人工例外只能由授权运营人员处理，并可完整审计。
5. 候补席位释放后及时处理并通知。建议基线：系统在席位释放后 5 分钟内完成自动转正并发起通知；最终时限以运营确认口径为准。
6. 让运营能按方向查看正式名单、候补队列、通知结果与例外记录，并在活动前完成容量核对。

### 非目标

- 不包含付费、退款、发票、现场签到或门票核销。
- 不做基于技能的智能推荐；参与者自行选择方向。
- 不支持同时选择多个方向，也不提供跨方向的偏好排序。
- 不负责方向内部的桌号、战队或更细粒度的小组编排；本系统的“分组”止于分配到一个能力方向。
- 不建设营销触达、CRM 或活动内容管理系统；仅发送报名、候补和变更所需的事务通知。

## 核心流程

### 1. 参与者报名

1. 参与者完成身份识别后进入报名页，看到报名截止时间、五个方向、每方向总名额、剩余名额和当前状态。
2. 参与者选择一个方向并确认提交。系统以服务端收到请求的时间判断是否截止，并校验该参与者没有另一条有效报名。
3. 系统在同一个原子操作内占用名额：方向尚有名额则状态为“报名成功”；名额已满则进入该方向候补队列。
4. 页面立即展示报名编号、方向、状态和提交时间；同时按已配置渠道发送通知。刷新或重复提交不得产生第二条有效报名。
5. 建议基线：截止前参与者可以取消或改选方向。改选按“释放原方向名额 + 申请新方向”一次性执行，任一步失败都不得形成双重报名或丢失原报名。

### 2. 候补与转正

1. 建议基线：候补按有效报名的服务端提交时间升序排列；同一请求重试不改变顺序。
2. 正式名额因截止前取消或运营调整而释放时，系统选择该方向最早且仍具候补资格的参与者转正。
3. 转正与名额占用必须原子完成，随后在建议基线 5 分钟内发起通知；通知失败不回滚已完成的转正，但进入运营待处理队列。
4. 被取消、已转正或被判定无资格的记录不再参与候补排序，系统继续处理下一名符合条件者。

### 3. 截止锁定与运营例外

1. 到达配置的截止时间后，系统拒绝新的参与者报名、取消和改选，并在界面显示“报名已截止”。已存在的报名结果保持可查看。
2. 运营人员仍可在后台搜索参与者、查看各方向名单和候补，并执行被授权的候补转正或人工例外。
3. 每次人工例外都必须填写原因，系统保存操作前后值、操作者和时间。默认不得突破“每方向 60 人”和“每人一个方向”；是否允许超额例外见待澄清问题 3。
4. 运营完成调整后复核方向人数、异常通知和未处理候补，并导出最终分组名单。

### 状态与转换口径

| 当前状态 | 触发 | 下一状态 | 操作主体 | 关键限制 |
|---|---|---|---|---|
| 未报名 | 截止前提交且有余量 | 报名成功 | 参与者 | 仅一个方向；原子占位 |
| 未报名 | 截止前提交且无余量 | 候补 | 参与者 | 进入所选方向队列 |
| 报名成功 | 截止前取消 | 已取消 | 参与者 | 释放名额并触发候补处理 |
| 报名成功/候补 | 截止前改选 | 新方向的报名成功或候补 | 参与者 | 原报名释放与新报名申请原子执行 |
| 候补 | 名额释放且轮到该参与者 | 报名成功 | 系统或运营 | 原子占位；记录转正来源 |
| 任一有效状态 | 截止后授权调整 | 调整后的状态 | 运营 | 必填原因、权限校验、完整审计 |
| 任一有效状态 | 截止后参与者操作 | 状态不变 | 参与者 | 返回已截止提示 |

## 需求

优先级定义：**P0** 为活动开放报名前必须具备的上线阻断项；**P1** 为不阻断首场活动、但会显著降低运营成本或风险的增强项。

| ID | 优先级 | 使用者 | 需求与可验收标准 |
|---|---|---|---|
| R-01 | P0 | 运营 | 可配置活动名称、时区、报名开始/截止时间，以及 5 个方向的名称与容量（本活动均为 60）；配置变更进入审计，报名开始后修改容量需二次确认。 |
| R-02 | P0 | 参与者 | 报名页展示五个方向的容量、实时剩余名额、是否已满、截止时间及个人当前状态；报名成功后展示的余量须反映本次占位结果。 |
| R-03 | P0 | 参与者/系统 | 同一参与者在任何时刻最多只有一个有效方向记录（“报名成功”或“候补”）；尝试再次报名时引导查看或修改原记录，不新增第二条有效记录。 |
| R-04 | P0 | 系统 | 名额校验与占用必须原子执行；在两个请求并发竞争最后一个名额时，只允许一个变为“报名成功”，其余进入候补，任一方向非例外正式人数不得超过 60。 |
| R-05 | P0 | 系统 | 提交、改选、取消和运营调整均支持幂等：重复点击、网络重试或页面刷新不产生重复记录、重复扣减名额或重复转正。 |
| R-06 | P0 | 参与者 | 每次提交后立即显示明确结果页，至少含报名编号、所选方向、当前状态、服务端提交时间和下一步说明；失败时说明原因并保留用户选择以便重试。 |
| R-07 | P0 | 参与者 | 按建议基线，截止前可取消或改选方向；取消成功后释放名额，改选必须整体成功或整体失败，失败时保留原有效报名并给出提示。 |
| R-08 | P0 | 参与者/运营 | 截止判定统一采用活动时区下的服务端时间；到点后参与者的新报名、取消、改选全部被拒绝并且状态不变，运营后台仍保留授权处理入口。 |
| R-09 | P0 | 参与者/运营 | 满额方向自动建立候补队列；按建议基线以服务端首次有效提交时间排序，并向参与者展示“候补中”和当前序号或“序号可能随资格处理变化”的说明。 |
| R-10 | P0 | 系统/运营 | 正式名额释放后，系统按队列顺序转正下一名符合资格者；转正、占位、原候补失效和审计记录一次完成。运营可对失败任务重试，但不得重复转正。 |
| R-11 | P0 | 参与者/运营 | 报名成功、进入候补、候补转正、取消和人工调整均生成事务通知；建议基线为转正后 5 分钟内发起发送。失败时自动重试并在运营后台显示失败原因及“重新发送”入口。 |
| R-12 | P0 | 运营 | 后台按方向显示容量、正式人数、剩余名额、候补人数与异常数；支持按报名编号或参与者标识搜索，并查看正式名单、候补顺序和通知状态。 |
| R-13 | P0 | 运营 | 仅授权角色可执行人工例外；提交时必须选择例外类型、填写原因并二次确认。默认仍校验每人一个方向和每方向 60 人，未获超额权限时不得保存突破约束的结果。 |
| R-14 | P0 | 运营/审计 | 对报名状态、方向、容量、候补顺序相关的每次变更保留不可由普通运营修改的审计记录，至少含操作者、角色、操作前后值、原因、时间和关联请求编号。 |
| R-15 | P1 | 运营 | 可按方向导出最终正式名单、候补名单、联系方式、状态、通知结果和例外标记；导出前显示生成时间与数据范围，且只有授权运营可下载。 |

## 异常与风险

### 1. 并发争抢最后名额导致超卖

- **场景与影响：** 多名参与者同时提交某方向最后一个名额；若先查余量再分别写入，正式人数可能超过 60。
- **系统处理：** 名额检查、占位和报名状态写入使用单一原子操作；失败请求转入候补；重复请求由 `request_id` 幂等处理。
- **运营处置与验收：** 后台显示容量异常告警并禁止普通运营继续增加正式名额。压测中并发争抢最后一个名额，只能产生一个正式报名，其余均为候补，且无重复记录。

### 2. 候补已转正但通知失败

- **场景与影响：** 名额已分配给候补者，但通知渠道超时或地址无效，参与者不知道已转正，可能造成席位浪费。
- **系统处理：** 转正事实不因通知失败回滚；通知按受控次数自动重试，持续失败则进入运营异常队列，并保存失败原因。
- **运营处置与验收：** 运营可筛出失败通知、核对联系方式并重新发送；每次重试留痕。故障演练中，通知服务恢复后可重试成功，且不会重复转正或重复占位。

### 3. 截止后人工调整造成规则冲突或越权

- **场景与影响：** 运营误将同一参与者放入两个方向、将方向人数调到 61，或无权限人员绕过截止锁定，最终名单失真且难以追责。
- **系统处理：** 后台按角色授权；例外必须填写原因并二次确认；默认继续执行“每人一个方向、每方向 60 人”。如未来允许超额，必须使用独立高权限和审批编号。
- **运营处置与验收：** 审计页可还原操作前后值、操作者、原因和时间，并支持按报名编号对账。无相应权限或缺少原因/审批时保存失败且原数据不变。

## 待澄清问题

1. **候补规则：** 是否确认按服务端首次有效提交时间排序并自动转正？转正后是立即生效，还是需要参与者在规定时间内确认，超时再顺延下一人？当前建议基线为“自动转正、立即生效”。
2. **截止前自助变更：** 参与者是否允许取消或改选方向，且释放的名额是否立即触发候补转正？当前建议基线为“允许，并立即触发”。
3. **人工例外边界：** 人工例外是否允许突破每方向 60 人；若允许，哪些角色可以操作、是否需要双人审批，以及活动总人数是否仍不得超过 300？当前安全基线为“不允许超额”。
